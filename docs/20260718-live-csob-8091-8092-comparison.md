# 8091 → 8092 CSOB 现场语义对照（1.14 录制，1.12 当前分析器）

## 结论

旧 18092 不是 18091 的状态复刻。它保留了目标侧自己的 `state/r/p` 演进，同时把设备展示改成另一套 profile，并产生大规模 `0x010A0024` 响应风暴。当前 1.12 active 实现针对这一问题只复制已证实的 `cs/ob/state/r/p`，目标账号、设备、report subtype、leaf、reserved 和 opaque tail 继续使用 8092 原值；匹配或校验失败时阻断该 CSOB，不上传原包。

## 流量与响应节奏

| capture | requests | responses | response/request | `0x010A0024` | 单请求 2 秒最大 `0024` | 请求后 `0024 > 3` |
|---|---:|---:|---:|---:|---:|---:|
| 18091 recording | 275 | 45 | 0.164 | 0 | 0 | 0 |
| 18092 old simulation | 299 | 940 | 3.144 | 900 | 32 | 57 |

18092 的 900 个 `0x010A0024` 中，834 个在 2 秒内关联到前序 `0x010A001B` 父请求，61 个关联到独立 `0x0102000A` 请求。主要 `field_c` 为 `0x00000194`（629 次）和 `0x00010194`（191 次）。这能证明它是重复响应反馈，但仅凭当前样本还不能把 `field_c` 固定解释为某个封号、白名单或大厅状态。

## 每类 reportCode 的证据边界

| reportCode | 当前能证明的角色 | 不能武断声明的内容 |
|---|---|---|
| `0x010A001B` | 父容器；承载多个 child，CSOB 状态通常位于动态 metadata child 内 | 父码本身不等于大厅/离线状态 |
| `0x0102000A` | typed leaf shell；必须用 `inner_type + selector0 + selector1 + inner_field + record_len` 完整 shape 分类 | 不能把所有该码 child 当成同一种数据，也不能把任意 BE32 当时间 |
| `0x010A0011` | 配对/保护上下文（观察） | 不能证明是固定高级白名单 |
| `0x011223xx` | 动态 metadata event family；本批次实际出现 CSOB、设备身份、应用版本、配置文件、证书/签名、运行时 API、Framework 和 opaque payload | 低字节 subtype 不是固定事件名称；同一 subtype 可承载不同 payload 角色 |
| `0x010A0010` | 响应反馈；两侧各 20 次，均可关联前序父请求 | `field_a/b/c` 的业务名称尚无证据 |
| `0x010A0024` | 18092 的高频响应反馈/风暴主体 | `0x194/0x10194` 目前只能作为风险反馈签名，不能直接命名为封禁码 |
| `0x010A0027` | 常规响应反馈；18091 为 21 次，18092 为 17 次 | 不用单个 field 值推断状态 |
| `0x010A0044` | 18091 观察到 1 次响应反馈，`field_c=0x6239` | 当前样本不足以命名 |
| `0x010A0057` | 18091 观察到 1 次全零响应反馈 | 当前样本不足以命名 |
| `0x010A0020` | 18091 观察到 2 次，均跟随父请求 | 目前不能证明含义 |

## 动态 subtype 为什么不能固定命名

以 `0x01122388` 为例：18091 的 9 次观察中有 5 次为完整 CSOB 状态快照、3 次为设备 profile 元数据、1 次为 opaque；18092 的 5 次观察中只有 2 次完整 CSOB、1 次设备 profile、2 次 opaque。因此 `0x88 = 状态包` 是错误归纳。当前报告同时展示 subtype 和 payload 角色，真正的状态判断以 payload 中同时存在 `cs/ob/state/r/p` 为准。

其他现场例子：

- `0x01122342` 主要承载设备 profile、IDFV/UUID 与应用版本元数据；
- `0x0112232E` 同时出现 `config2.dat/config3.dat` 配置文件观察和 opaque 数据；
- `0x01122338/57` 出现 `addListener`、`HDMIOutput` 等运行时 API/输出路由观察；
- 部分 subtype 出现 Apple Root CA、TeamID、Framework 或编码后的客户端组件名称。

这些是 payload 证据角色，不是对 subtype 的永久协议命名。

## 状态差异

18091 的完整 CSOB 样本以 `state:00b00017` 为主，并包含首次 `00300015`；18092 旧仿真仍出现目标侧自己的 `00b00017/00d00017` 演进。两侧 `p` 基准也不同（现场主要为 5448 与 1036），说明旧链路没有复制状态，只是在其他位置修改了设备/身份相关内容。

当前 active 算法允许动态 CSOB child 因目标身份文本长度不同而采用 semantic-compatible 匹配，但要求五个字段齐全且顺序一致。离线结果为 6/6 父请求成功重建，6/6 加密往返一致，目标身份与 opaque tail 100% 保留。

## 时间戳修复验收

| capture | 接受的时间字段 | 拒绝的普通 BE32 候选 |
|---|---:|---:|
| 18091 | 18（6 组 `ob:T1/T2/T3`） | 4800 |
| 18092 | 15（5 组 `ob:T1/T2/T3`） | 4528 |

被拒绝项分为：普通 BE32 没有 schema 时间角色、落入 ASCII/hash/string 槽、跨越 schema/string 字段边界。child `+0x44 = ASCII dd3b` 已有回归测试并保持拒绝，不再高亮为时间戳。
